MedInsight AI: A Conversational LLM Interface for Exploring Large-Scale Indian Medicine Data

Narendra Somnath Vispute · Data Analyst and Data Scientist, Mumbai, India · October 2026

Abstract. Indian pharmaceutical data is large, wide and uneven, which makes it hard for non-programmers to query. This paper presents MedInsight AI, a Streamlit application that lets users ask plain-English questions about a medicine table and receive a language-model answer together with an automatically selected chart. The system couples pandas profiling, a compact dataset summary, Groq-hosted LLaMA 3.3 70B, and a keyword-routed Plotly chart generator. We profile the bundled dataset of 248,218 medicine records and 58 columns, find that 69.5% of its cells are empty because of a wide side-effect layout, and analyse how the design behaves on it. We identify three limits: the model sees only a truncated summary, the chart router is disconnected from the model, and price-oriented features described in the project README cannot be supported by the bundled data. We propose a retrieval-and-execution architecture to address them.

Keywords: conversational analytics, large language models, pharmaceutical data, Streamlit, data visualisation, text-to-analysis

1. Introduction

India has one of the largest retail medicine markets in the world, and product information is spread across thousands of brand names that share a small number of active ingredients. Pharmacists, students and health-data analysts often need simple answers: which therapeutic classes dominate, which side effects are most commonly listed, which substitutes exist for a brand. Answering them today means writing SQL or pandas code, which excludes most of the people who ask.

Large language models (LLMs) offer a natural interface to tabular data, because a person can phrase a question in English and read the answer in English.[1] MedInsight AI applies this idea to medicine records. A user uploads a CSV file, sees an instant overview, and chats with the data while the application draws a chart next to each answer.

Contributions. (i) A complete, small and deployable architecture for conversational medicine analytics. (ii) A quantitative profile of the dataset the project ships with, including its structural sparsity. (iii) A critical evaluation of where the current design is reliable and where it is not. (iv) A concrete redesign that grounds answers in executed queries rather than a truncated text summary.

2. Background and Related Work

LLMs for data questions. General-purpose LLMs such as GPT-3[1] and the open LLaMA family[2] can follow instructions and summarise tables that fit in a prompt. Their weakness is that arithmetic over a table too large for the context window is guessed, not computed, and fluent but unsupported output is a documented failure mode.[3]

Grounding. Retrieval-augmented generation supplies the model with evidence fetched at query time instead of relying on its parameters.[4] For tabular data the analogue is to let the model write a query, execute it, and narrate the result. MedInsight AI currently sits one step earlier in this progression: it supplies a summary rather than retrieved rows.

Classical prediction. Random forests[5] implemented in scikit-learn[6] are a common baseline for tabular regression. The project README names a Random Forest price model as a planned module; Section 7 explains why this cannot be evaluated from the submitted files.

3. Dataset

The bundled file medicine_dataset.csv (about 89 MB) holds 248,218 records and 58 columns. The layout is: an integer id; the brand name (222,825 distinct values); five substitute slots; forty-two sideEffect slots; five use slots; and four categorical fields, Chemical Class, Habit Forming, Therapeutic Class and Action Class. The only numeric column is id.

Lists are stored in a wide layout, one slot per list item. Because most medicines list only a handful of side effects, the table is structurally sparse: 10,002,467 of 14,396,644 cells (69.5%) are empty. Use the figure below to explore the distribution. Click any bar to read its share of the whole table.

Three properties matter for analytics. First, the Therapeutic Class field is complete and has 22 values, so it is the most reliable grouping key. Second, Chemical Class and Action Class are empty for about 44% of records, with 872 and 431 distinct values respectively. Third, medicines list on average 6.49 side effects (median 6, maximum 42), 4.65 substitutes and 1.46 uses. Only 2.4% of records (6,003) are flagged habit-forming.

4. System Architecture

The application is about 300 lines of Python in four modules: app.py (interface), utils.py (loading and summarising), gemini_engine.py (LLM calls; the file name is historical, the client is Groq) and chart_generator.py (visualisation). Select a stage to see what it does.

5. Implementation

5.1 Ingestion and summary

Uploaded CSVs are read with low_memory=False and text columns are whitespace-stripped. To control cost, get_dataframe_summary builds a description of shape, column names, a five-row sample and describe() output, then truncates it to 3,000 characters. A second sample of five rows is sent alongside it.

5.2 Language model

Each question is wrapped in a prompt that casts the model as an expert analyst of Indian pharmaceutical data, adds the summary and sample, and asks for exact figures and a suggested chart type. The call uses llama-3.3-70b-versatile with max_tokens=1000 and temperature=0.7. A separate call generates six suggested questions when a dataset loads.

5.3 Chart routing

The question is lower-cased and matched against keyword lists in a fixed order; the first matching branch wins. Column names are then resolved by substring search, with a fallback to the first text or numeric column. The routing is reproduced in Figure 3.

5.4 Interface

The dark Streamlit interface provides dataset statistics, tabs for preview, statistics, missing values and column information, a chat panel with persisted history, per-session query counter, and text export of the conversation.

Observed strengths

Setup is minimal, the interface is approachable, and the deployment is live. The suggestion step helps users who do not know what to ask, and the session export supports reporting.

Observed weaknesses

The model answers from a truncated summary

The 3,000-character summary is dominated by column names and sample rows. With 248,218 records, any aggregate the model reports is an estimate from five rows unless the answer is general pharmacology knowledge. The prompt asks for “exact figures”, which invites confident fabrication.[3]

The chart is not tied to the answer

Chart selection uses the question text only, so the plot can disagree with the prose. Because routing runs by substring, “stop” contains “top” and triggers the company bar chart.

Keyword fallbacks mislead on this dataset

The router assumes price, manufacturer and category columns. None exist here, so it plots whichever column is first. The first column containing “class” is Chemical Class (44.5% missing), shadowing the complete Therapeutic Class.

Sparse wide columns are invisible to the model

Forty-two side-effect columns are 84.6% empty. A long-format (one row per medicine–side-effect pair) table would make counts trivial.

7. Limitations and Threats to Validity

Data and claims. The README reports a price model (Random Forest, 40,000+ samples, 85%+ accuracy) and 1,000+ companies. The submitted archive contains no ml_model.py, no price or manufacturer column, and no training log, so these figures could not be reproduced and are not claimed here. Readers should treat them as unverified until the code, split and metric definition are published.

Scope. The system reports what a dataset lists; it is not clinical advice, and side-effect presence says nothing about frequency or severity. The data source and licence are not documented in the repository, which limits reuse. Security. Hosting an application with a third-party API key requires secrets to be kept out of version control and rotated if exposed.

8. Proposed Improvements

The central change is to make the model compute instead of recall. Let the model emit a structured pandas query (or a constrained JSON plan); execute it in a sandbox; pass the resulting table back for narration; and draw the chart from that same table. This ties prose, number and figure to one source, and lets the system say “this column does not exist”.

Secondary work: reshape list columns to long format; add a semantic schema map (for example, “category” means Therapeutic Class); lower temperature to 0.2 for analytic answers; add a small gold set of 50 questions with checked answers to measure accuracy; and add medicine search by retrieval[4] for substitute lookup. A price model should only return after a price field with a documented source exists, and with a held-out evaluation.

9. Conclusion

MedInsight AI shows that a few hundred lines of Python can turn a 248,218-row medicine table into a conversational tool with charts. The same profiling exposes the gap between a convincing interface and a reliable analyst: answers rest on a five-row sample, the chart router is decoupled from the model, and its keyword assumptions do not fit the data. Executing model-written queries against the full table, and publishing an evaluation set, would turn the prototype into something whose answers can be checked.
